# Corn Kidz 64 → Nintendo 64 — Phase 3: `Data` and save format

**13 November 2026.** Status: source-driven analysis + a tested portable C11 save module. **Not** an N64 build, playable scene, libdragon integration, .cow import or console validation.

## Original source evidence (Windows Unity Mono)

- Recovered all **34** fields of `Data` from the original `Assembly-CSharp.dll` Field table/signature blobs. See `reports/data_fields.json`, generated by `tools/inspect_data_fields.py`.
- `GameCtrl.ResetSav` **explicitly overwrites 20 fields**, including 6 allocated arrays; it **does not reset 14 other settings**. We have verified these method instructions directly in `reports/gamectrl_il.json`. This is an important correction over the previous broad assumption that all settings become zero on reset.
- Array lengths from IL: `switches[1000]`, `items[1000]`, `upgrades[100]` as booleans; `ints[100]`, `cranks[100]`, `lvlItems1[100]` as signed 32-bit integers.
- Reset defaults: `currentLvl=1`, `maxHP=8`, item/other designated counters `0`, and newly allocated arrays zeroed.
- The source `SaveGame` serializes the entire `Data` object via .NET `BinaryFormatter` at `<persistentDataPath>/save1.cow`; original `LoadGame` deserializes it. The new N64 format is intentionally **not** binary-compatible with `save1.cow`.
- The first instructions of `GameCtrl.Update` increment `sceneTimer` and `activeTime` unconditionally, increment `Data.gameTime` only if `currentWorld > -100`, and clamp HP below zero to zero. We implemented **only this subset**, not `MusicFade` or debug keyboard actions.

### Native save record v1

File/record length: **1,533 bytes**. This is one record, not a game cartridge ROM.

| Offset | Size | Meaning |
| --- | ---: | --- |
| 0 | 8 | ASCII `CK64SAVE` |
| 8 | 2 | Version 1, u16 BE |
| 10 | 2 | Reserved = zero |
| 12 | 4 | Payload bytes = 1513, u32 BE |
| 16 | 4 | CRC32 (ISO-HDLC / Python `zlib.crc32`) over payload only, u32 BE |
| 20 | 125 | Switch bits `[0..999]` |
| 145 | 125 | Item bits `[0..999]` |
| 270 | 13 | Upgrade bits `[0..99]`, four high unused bits required to be zero |
| 283 | 400 | `ints`, 100 big-endian signed i32 |
| 683 | 400 | `cranks`, 100 big-endian signed i32 |
| 1083 | 400 | `lvlItems1`, 100 big-endian signed i32 |
| 1483 | 48 | Twelve signed i32: `itemTotal`, `currentLvl`, `HPupTotal`, `screwTotal`, `maxHP`, `totalDeaths`, `gameTime`, `currentCamMode`, `ctrlType`, `clothes`, `volume`, `antialias` |
| 1531 | 2 | Flags BE u16: bit 0 `bNonEmpty`, bit 1 `camInvertOff`, bit 2 `bRumble`, bit 3 `bSkipLauncher`, bit 4 `bFullscreen`, bit 5 `bWidescreen`, bit 6 `bVsync`, bit 7 `bRAnalogDpad`, bit 8 `bAnalogX2`, bit 9 `b1080`, bit 10 `bIgnoreDpadX`, bit 11 `bP1only`, bit 12 `bMusic`, bit 13 `bAchDisable`, bit 14 `b60fps`, bit 15 `bForce60hz` |

Bits in bitmap arrays are LSB-first inside each byte, independent of CPU endianness; all multi-byte integers are big-endian. Read operations validate signature, version, exact length, reserved flags and CRC before modifying caller state. No `sizeof(struct)` serialization; no unaligned 32-bit reads or pointer-size assumptions.

**ROM save-device caveat:** 1,533 bytes can fit in the **16-Kbit (2,048-byte) N64 EEPROM** used by some cartridges, assuming an available device with adequate capacity; it cannot fit in 4-Kbit (512-byte) EEPROM without another encoding or storage device. Controller Pak is another candidate. **No EEPROM/Pak driver is present**. This is not a claim of actual on-console save functionality. Hardware support and possible journaling/atomic writes are future tasks.

## Verification performed

```sh
cmake -S portable -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build
ctest --test-dir build --output-on-failure
# Two CTest suites pass: 10 gameflow + 8 save scenarios, 18 groups in total.
python3 tools/verify_phase3_evidence.py .
# 13 static IL/schema checks pass.
```

Also tested using GCC 14.2 with `-fsanitize=address,undefined -fno-sanitize-recover=all -fno-omit-frame-pointer`; both CTest suites pass. This checks host behavior but cannot establish N64 behavior. An independently calculated default-record CRC (`0x84CA69DD`, Python zlib) is included as a regression golden.

## Remaining tasks/risks

1. This is a **versioned custom N64 file format**, not a converter for .NET `BinaryFormatter`. A safe offline exporter could eventually read a lawful user's `.cow` file using an appropriate trusted .NET environment. Do not deserialize untrusted BinaryFormatter files directly.
2. Save IO callbacks still have no concrete N64 implementation (libdragon EEPROM/Controller Pak) and need error handling, device detection, write failure recovery and wear considerations.
3. `Data` field names/types are verified, but game-state meaning for many fields and their uses by other MonoBehaviour classes are not yet reconstructed. `ResetSav` and portions of `GameCtrl` were inspected statically, not gameplay-traced.
4. `GameCtrl.Update` counters reject `INT32_MAX` overflow to avoid C undefined behavior; the managed IL could wrap. It does not implement `MusicFade` or debug input.
5. The scene registry, player controller, camera, collision, assets/audio and Nintendo 64 graphics are not implemented; **no ROM has been compiled or executed**. Cross-compiler and emulator not available in this container.
6. No game files are redistributed in the downloadable package.

**Next module:** Continue `GameCtrl.MusicFade` / audio abstraction or recover the canonical scene/door table, then begin minimal libdragon integration only after those behaviors are cleanly separated.
